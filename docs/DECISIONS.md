# Prototype defaults and decision log

Mirror of the table "Prototype defaults and decision log" in the
[HLD](https://claude.ai/code/artifact/d7fce61b-0fe9-4bae-a8b2-7286684b9de4). If the two disagree, the HLD wins.
D1–D18 were set before the build; D19 onwards were added while building, following handover section 13.

This file is the single decision log for all three repos (hsrp-dms-be, hsrp-dms-fe, hsrp-dms-android); the
frontend and Android repos link here. Add a decision with the maintain-docs skill: next free number, append a row
here **and** to the HLD table (append only, never edit existing rows).

| D45 | Plate photo OCR after embossing and at fitment | Two OCR gates on the registration number. (1) After embossing, the station photographs each plate on the QC screen (POST /station/qc/:orderId/plate-photos); QC "Pass" is refused until every allocated plate has a passing reading (setting production.plateOcrRequired, default true). (2) At fitment, the front and rear plate photos are read before the fitment is recorded; a mismatch refuses the fitment with 422 plate-ocr-mismatch (setting fitment.plateOcrRequired, default true). Rule: the text read must contain the ordered registration number exactly (letters and digits only, spaces ignored); nothing read is a failure. Every reading is kept (core_prd_photo_check, core_fit_photo_check, refused fitment attempts included) and shown on the order and in the "Plate photo checks (OCR)" report. OCR is a port (PlateReader) with two adapters chosen by OCR_ADAPTER: tesseract (default; tesseract.js in the API process with the bundled English model, nothing downloaded at run time) and mock (reads the plate text that test images embed after "HSRP-PLATE:"). OCR runs inside the request because it is local and takes ~0.1–1 s. | Claude Code, 12 Oct 2026 (user request) |
| D46 | Postpaid billing per OEM, bill-to per OEM × dealer | Payment mode is set per OEM (setting billing.paymentMode: PREPAID = today's wallets, POSTPAID). A postpaid OEM's orders are confirmed without a wallet hold (order-flow) and become charges in the new billing module (core_bil_charge): PENDING at confirmation, BILLABLE when the plates are dispatched, VOID if cancelled or rejected first. Each OEM has a billing cycle (billing.cycle: WEEKLY closes Monday 00:00 IST, MONTHLY the 1st 00:00 IST); an hourly job closes due cycles once (core_bil_run makes it idempotent) and "Run billing now" closes the current period early. A run makes one bill per bill-to party with the dispatched charges, renders a PDF (template bill, numbers BL{YY}{MM}-) and e-mails it (template BILL_ISSUED) to the dealer's e-mail or the OEM's billing contact (billing.contactEmail). Bill-to is set per OEM × dealer (billing.billTo, scope oem-dealer "OEM:DEALER"), falling back to the OEM's default, then the OEM; it is fixed on the charge at confirmation. Seed: Zenmo postpaid monthly, billed to Zenmo except WB02 (dealer); Kranti prepaid. Orders without an OEM and customer orders stay prepaid. No tax invoice in the prototype. | Claude Code, 13 Oct 2026 (user request) |
| D47 | Bulk upload of OEM data from the admin portal | Besides the OEM integrations (API, per-OEM files), two standard import templates serve every OEM: OEM_VEHICLES_STANDARD (vehicle data) and OEM_ORDERS_STANDARD (orders). The OEM is chosen at upload and passed as import context; profiles can declare requiredContext (the import refuses an upload without it) and columnOrder, and GET /imports/profiles/:code/template returns the template CSV with an example row. Uploaded on OEM files & uploads → Bulk upload OEM data. Rows go through the same targets as the integrations (vehicle data, OEM orders), so the same checks apply (e.g. the dealer must be mapped to the OEM). | Claude Code, 13 Oct 2026 (user request) |
